[[Projects/customer-analytics-mart/index|프로젝트 개요]]로 돌아가기

앞의 네 편은 전부 사후 분석이었습니다. 이전 회사 DB에 물려 있던 프로젝트라 `dbt parse`조차 안 됐고, "숨은 엣지"나 "알려진 버그 3종" 같은 결함은 코드를 읽고 추론만 할 뿐 실제로 재현하거나 고쳐볼 방법이 없었습니다. 그래서 DuckDB로 로컬 샘플을 만들어 복원하기로 했습니다. 모델 62개를 T-SQL에서 DuckDB 문법으로 포팅하고, 외부 테이블 42개는 구조만 맞춘 합성 seed로 대체했습니다. 값이 사실적일 필요는 없었습니다 — 목표는 오케스트레이션이 실제로 돌아가는 것, 그리고 진단 문서에 적어뒀던 결함들을 진짜로 재현하고 고쳐보는 것이었습니다.

## 리뷰 파이프라인을 먼저 세웠다

스캐폴드가 끝난 뒤 곧바로 코드를 고치지 않았습니다. 대신 dev·docs·review·security 4개 부서로 나눠 작업하는 파이프라인부터 만들었습니다. 커밋마다 `Dept:`/`Reviewed-by:`/`Security-check:` 트레일러를 남기고, dev가 뭔가를 고치면 review가 별도 세션에서 duckdb를 다시 빌드해 대조하고, security가 자격증명·민감정보를 훑는 구조입니다. 원본 프로젝트를 다시 찾아보니 `H:\dbt\...`가 실은 원격 없는 로컬 전용 git 저장소였습니다. 커밋 2개, 리뷰어 0명. "SP → dbt 이관이 70% 지점에서 멈췄다"는 진단이 왜 그렇게 됐는지 이제 조금 더 납득이 갑니다 — 절반만 옮겨놔도 아무도 걸러내지 못하는 구조였다면, 멈추는 게 오히려 자연스럽습니다.

규칙은 하나였습니다. **버그를 발견하면 먼저 실패하는 재현 테스트를 짜고, 그 테스트가 확실히 빨간불인 걸 확인한 다음에야 고칩니다.** 순서를 바꾸면 "테스트가 통과한다"는 말이 아무 의미가 없어집니다.

## add_month — 8을 그대로 옮긴 게 화근이었다

첫 번째는 `add_month` 매크로였습니다. `returnstring` 파라미터를 받아놓고 본문에서 한 번도 안 쓰는 바람에 6자리(YYYYMM)든 8자리(YYYYMMDD)든 요청과 무관하게 항상 6자리만 돌려주는 버그입니다. 재현 테스트는 간단했습니다 — 같은 인자로 `add_month(6,...)`와 `add_month(8,...)`를 호출해서 결과가 같거나 8자리 요청인데 길이가 8이 아니면 실패.

고치는 과정에서 더 흥미로운 게 나왔습니다. 프로젝트 전체에서 `returnstring=8`을 요청하는 호출부 6곳 중 5곳이 `POMSUB_CUSTOMER_POL_BASE.sql`에 몰려 있었는데, 그 바로 위에 남아있던 원본 T-SQL 주석을 보니 전부 `SUBSTRING(CONVERT(VARCHAR(8),...),1,6)` 형태였습니다. 8자리로 변환한 다음 다시 6자리로 잘라 쓰는 게 원래 의도였던 겁니다. 포팅할 때 `VARCHAR(8)`이라는 표기만 보고 8을 그대로 옮기면서, 뒤이은 `SUBSTRING(...,1,6)` 절단을 놓친 겁니다. 그러니까 매크로를 고치면서 이 5곳까지 8로 그대로 뒀다면, 지금까지 버그난 매크로 덕분에 우연히 맞아떨어지던 값이 진짜로 깨질 뻔했습니다. 5곳을 전부 6으로 되돌리고 나서야 매크로 수정 전후로 값이 안 바뀝니다 — "버그를 고친다"는 게 이번엔 원본 의도로 되돌리는 일이었습니다. 진짜 8자리가 필요했던 곳은 `POMSUB_CUSTOMER_POL_DATA.sql` 한 곳뿐이었고, 이마저도 앞단의 `LifeAgreeYN = 'Y'` 게이트가 합성 데이터에서 한 번도 참이 되지 않아 실제 산출값은 안 바뀌었습니다.

## 버그를 잡는 테스트에도 버그가 있었다

세 번째 버그(기간계 직접 참조 모델 11개, campmonth 미반영)를 잡으려고 구조적 테스트를 하나 짰습니다. 11개 모델의 원본 코드를 훑어서 `var("campmonth")`나 `add_month(` 같은 토큰이 하나도 없으면 그 모델명을 결과로 반환하는 테스트입니다. 처음 짠 버전은 이랬습니다.

```jinja
{% set has_filter = false %}
{% for token in campmonth_tokens %}
  {% if token in code %}
    {% set has_filter = true %}
  {% endif %}
{% endfor %}
{% if not has_filter %}
  {% do offenders.append(node.name) %}
{% endif %}
```

리뷰에서 걸렸습니다. Jinja2는 `{% for %}` 바디 안에서 한 `{% set %}`을 그 루프 바디 안에서만 유효하게 스코프합니다. 즉 안쪽에서 `has_filter = true`로 갱신해도 바깥 스코프의 `has_filter`는 항상 최초값(`false`)에 머뭅니다. `{% if not has_filter %}`는 조건이 아니라 사실상 상수 참이었던 겁니다 — 11개 모델을 전부 고쳐놓고 실행해도 여전히 11행이 나오는 테스트였습니다. 리뷰가 "이 11개 모델이 이미 다 고쳐졌다고 가정하고 시뮬레이션해도 여전히 11행이 나온다"는 걸 직접 재현해서 지적했습니다.

고친 버전은 불리언 대신 리스트를 씁니다.

```jinja
{% set matches = [] %}
{% for token in campmonth_tokens %}
  {% if token in code %}
    {% do matches.append(1) %}
  {% endif %}
{% endfor %}
{% if matches | length == 0 %}
  {% do offenders.append(node.name) %}
{% endif %}
```

리스트는 `.append()`로 같은 객체를 그대로 변형하기 때문에 루프 바깥에서도 값이 유지됩니다. 수정 후에는 가짜 모델 코드 문자열 4개(토큰이 있는 것 3개, 없는 것 1개)로 옛 로직과 새 로직을 나란히 돌려봤습니다. 옛 로직은 토큰이 있는 것까지 포함해 4개 전부를 오탐(offender)으로 판정했고, 새 로직은 토큰 없는 1개만 정확히 걸러냈습니다. 재현 테스트 자체도 재현 테스트가 필요했던 셈입니다.

## campmonth인 줄 알았는데 ltddashmonth였다

11개 모델 중 치과 만기 대시보드(`Maturity_Count`)는 조금 다르게 걸렸습니다. 컬럼명이 `CAMPYM`이길래 `campmonth`로 필터를 걸었고, `--vars`로 다른 달을 넣어봤더니 결과 행수가 바뀌는 것까지 확인하고 통과로 표시했습니다. 그런데 리뷰가 짚었습니다 — 같은 파일 안의 다른 CTE(`LTD_MAT_ACT`)가 이미 `ltddashmonth`라는 별개의 변수로 스코프돼 있었고, `dentalMaturity_DashBoard/schema.yml`에도 이 대시보드의 기준월은 `ltddashmonth`라고 적혀 있었습니다. `campmonth`는 이 파일 어디에도 등장한 적이 없었습니다.

더 뼈아픈 건 "검증"이라고 했던 실험이 사실 아무것도 증명하지 못했다는 점입니다. `--vars '{campmonth: "202409"}'`로 결과가 바뀐다고 확인했었는데, 그 값이 `ltddashmonth`의 기본값과 우연히 같은 숫자였을 뿐입니다. `campmonth`를 바꿔서 결과가 바뀐 게 아니라, 어쩌다 `ltddashmonth`와 같은 숫자를 넣었을 때만 결과가 바뀐 것처럼 보인 겁니다. 컬럼명 패턴만 보고 변수를 골랐다가, 같은 파일에 이미 있던 스코프를 놓칠 뻔한 사례입니다. `ltddashmonth`로 바꾸고 나서야 기본값 기준 결과가 그대로(2행) 유지됐습니다.

## 그 밖에 리뷰가 잡아낸 것들

몇 가지는 짧게만 남깁니다. 보안 검토에서 `dbt` 프로필 이름이 전역 `~/.dbt/profiles.yml`에 이미 있던 동명의 프로필과 겹친다는 걸 발견했습니다. 그 전역 프로필은 이전 회사 SQL Server의 평문 자격증명을 담고 있었고, 이름이 겹치면 `--profiles-dir` 없이 실행할 때 그쪽으로 fail-open될 위험이 있었습니다. 프로필 이름을 바꿔서 fail-closed로 정리했습니다. Dagster 쪽에서도 비슷한 패턴이 하나 있었습니다 — 커스텀 DQ 체크 하나가 `dbt` 실행마다 새로 생기는 target 디렉터리가 아니라 최상위 `run_results.json`을 읽고 있어서, 과거에 수동으로 한 번이라도 빌드를 돌린 적이 있으면 이번 실행과 무관하게 그 결과로 "통과"가 뜨는 fail-open 체크였습니다. 고치는 대신 삭제했습니다 — 이미 개별 asset check 268개가 같은 정보를 더 정확하게 덮고 있었습니다.

가장 인상 깊었던 건 "빌드가 통과한다"와 "값이 맞다"는 다른 말이라는 걸 숫자로 본 순간이었습니다. `dbt build`가 `PASS=96 ERROR=0`을 찍었을 때, 그중 29개 모델이 합성 데이터 8행 기준으로 조용히 0행을 산출하고 있었습니다. SQL은 파싱되고 실행도 됐지만, "이 조건에 걸리는 값이 실제로 하나는 있다"는 건 아무도 확인한 적이 없었던 겁니다. 이후 각 seed의 값 분포를 하나씩 손봐서 공허 테스트 비중을 53%(151/287)에서 18.8%(54/287)까지 줄였습니다. 나머지는 조인 키 도메인이 애초에 안 겹치는 등 seed 몇 개를 더 손봐야 하는 구조적인 문제라 원인만 문서에 남기고 다음으로 미뤘습니다.

## 남은 버그 셋도 마저 고쳤다

만기·환급 계열 모델 5개는 조인 키로 쓰는 두 컬럼(`treatyCoverageCode`, `treatyCode`)의 값 도메인 자체가 애초에 안 겹쳐서 항상 0행이었습니다. seed 값만 손대고 모델 SQL은 그대로 뒀는데, 어느 쪽 코드 체계로 맞출지도 그냥 정하지 않았습니다 — 이미 다른 모델 6개가 쓰고 있던 체계를 살리고 반대쪽을 거기 맞췄습니다. 결과 행이 나오기 시작한 뒤에는 행 하나하나를 어떤 필터가 통과시켰는지 역추적해서, 우연히 남은 값이 아니라 실제 로직이 골라낸 값인지 확인했습니다. 테스트에도 "1행 이상"이 아니라 정확한 행수 범위를 박아뒀습니다 — 예전에 seed 키가 중복돼 허브 모델이 조용히 4배 부풀었던 적이 있었는데, 같은 종류의 사고가 또 나면 이번엔 소리 없이 통과하지 않도록요.

`POMSUB_DNCCampaign`의 날짜 역전 버그(하한이 상한보다 항상 큰 BETWEEN)도 고쳤습니다. 원본 T-SQL을 직접 대조해 포팅 과정에서 생긴 게 아니라 원래부터 있던 결함이라는 걸 확인했고, 이 프로젝트의 다른 모델 6개가 이미 쓰고 있던 "이미 일어난 일"용 과거 윈도우 관례를 그대로 따랐습니다. `POMSUB_TEMP_ILISA_CALL_ERROR`도 형제 모델과 같은 패턴(campmonth 상한 없이 무조건 최신 레코드가 이김)이라 같은 방식으로 고쳤습니다.

## 결과와 남은 것

재현 테스트는 전부 통과로 바뀌었고, 기존 데이터 테스트는 단 한 건도 회귀하지 않았습니다. `dbt build`는 최종 `PASS=403 / ERROR=0`, `dbt test`는 `PASS=308 / ERROR=0`입니다. Dagster 쪽은 asset 95개(dbt 모델 62 + seed 42, ephemeral 9개는 물리 테이블이 없어 그래프에서 자연스럽게 빠짐)와 asset check 269개까지 실제 머티리얼라이즈로 확인했습니다.

남은 건 이제 많지 않습니다. `dbt docs`와 Dagster UI 스크린샷이 아직이고, 형제 모델끼리 조인 윈도우 폭이 미묘하게 다른(M+2 vs M+3) 것 같은 사소한 항목 몇 개가 다음 라운드 후보로 남아 있습니다. 발행 전에 정작 제일 먼저 처리해야 할 건 따로 있었습니다 — 보안 검토에서 모델 파일 48개의 헤더 주석에 원작자 실명이 그대로 남아있는 걸 찾았습니다. 브랜드명이나 내부 시스템명보다 훨씬 민감한, 실존 인물의 개인정보입니다. 코드 스니펫을 인용할 땐 헤더 블록부터 잘라내야 합니다.

원본은 로컬 저장소 하나에 커밋 2개, 리뷰어는 없었습니다. 이번엔 같은 코드를 리뷰가 세 번씩 되돌려 보내는 라운드가 여러 번 있었습니다. 결함을 만드는 것도, 결함을 잡는 도구를 잘못 만드는 것도 똑같이 쉽다는 걸 이번에 알았습니다 — 차이는 그걸 걸러내는 두 번째 시선이 있느냐였습니다.
