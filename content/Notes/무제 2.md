# 분석가 시스템 프롬프트 팩 + 리포트 자동화 대화 설계 — 난이도: 상

> **시간:** 4시간 · **도구:** 채팅 플랫폼(ChatGPT·Claude·Gemini) + Colab(전처리·요약) · **API 키 불필요**
> **한 줄:** 매번 새로 프롬프트를 짜는 대신, **재사용 가능한 시스템 프롬프트 팩 2~3종**을 직접 설계하고,
> **멀티턴 대본**으로 리포트를 완성하며, **검증 로그(숫자 대조)** 까지 남기는 "설계자"가 됩니다.

## 0. 한 줄 소개 / 완성하면 무엇이 남는가

**한 줄 소개.** 하는 일이 다른 세 상황(매출·리뷰·KPI)에 각각 맞는 **시스템 프롬프트 팩**을 설계하고,
**멀티턴 대화 대본**으로 리포트를 조립하며, AI가 쓴 숫자를 파이썬 값과 대조한 **검증 로그**를 남깁니다.

**완성하면 남는 것 (A와의 결정적 차이 = 재사용 자산)**

```
🎁 재사용 프롬프트 팩 (팀에 물려줄 수 있는 자산)
├─ 팩① 매출 리포트용 시스템 프롬프트   (구조화 + few-shot + 검증)
├─ 팩② 리뷰 요약용 시스템 프롬프트     (구조화 + few-shot + 검증)
└─ 팩③ 주간 KPI용 시스템 프롬프트      (구조화 + few-shot + 검증)

📜 멀티턴 대본  — "이 순서로 이렇게 말하면 리포트가 완성된다"는 대화 각본
🧾 검증 로그    — AI 숫자 vs 파이썬 숫자 대조표 (통과/불통과 기록)
📄 통합 주간 리포트 — 위 3개를 엮은 한 장짜리 경영 리포트
```

> 🎯 A가 "리포트 1개를 만든다"면, B는 **"리포트를 매주 같은 품질로 찍어낼 시스템을 설계한다."**

## 1. 실무 시나리오 (어떤 회사의 어떤 문제인가)

여러분은 **온라인몰 데이터팀의 실무자**입니다. 경영진은 매주 **세 가지**를 봅니다.

```
① 매출이 어땠나 (요일·카테고리)      → 마케팅 팀장이 봄
② 고객 반응이 어땠나 (리뷰·별점)     → CS/상품 팀장이 봄
③ 핵심 지표 한눈에 (KPI)             → 대표가 봄
```

**문제.** 세 리포트는 **독자도 톤도 형식도 다릅니다.** 매주 프롬프트를 새로 짜면 품질이 들쭉날쭉하고, 실수로 숫자를 지어내기도 합니다.

**해법(PoC).** 상황별 **시스템 프롬프트를 '팩'으로 표준화**하면, 누가 언제 돌려도 **같은 형식·같은 검증 규칙**으로 리포트가 나옵니다. 이게 6주차 API 자동화의 **설계 원본**이 됩니다.

> 💡 이 프로젝트의 진짜 산출물은 리포트가 아니라 **"리포트를 만드는 시스템(프롬프트 팩 + 대본 + 검증)"** 입니다.

## 2. 사용 데이터 (출처·URL·라이선스·다운로드)

`solution_data_prep.py` 가 **전처리가 필요한 원본**에 가까운 데이터를 생성합니다(취소주문·결측·문자열 날짜 포함) + 익명 합성 리뷰.

```

#   URL: https://archive.ics.uci.edu/dataset/352/online+retail
#   라이선스: CC BY 4.0 (데이터셋 페이지에서 최종 확인)

#   실무 해석: 온라인몰 주문 원본. 확인일: 2026-07-13
#
# [리뷰 데이터] 개인정보 없는 익명 리뷰로 교체(공공데이터포털/Kaggle 공개 리뷰 등).
#   사용 전 라이선스·개인정보 여부 확인. 본 스크립트는 저작권·개인정보 이슈가 없도록
#   한국어 리뷰를 '합성'해 생성합니다.
```

- **왜 지저분한 데이터인가?** 난이도 상은 **약간의 전처리**를 포함합니다(취소 제거·결측 보정·날짜 파싱). 실무의 현실을 축소판으로 경험합니다.
- **다운로드/교체.** 실제로 쓰려면 `generate_raw_orders()` / `generate_reviews()` 를 `pd.read_csv(...)` 로 바꾸고 컬럼명만 맞추면 됩니다.
- **개인정보 없음.** 리뷰는 합성 문장, 고객 식별자는 생성하지 않습니다.

## 4. 성공 기준 (체크박스 — 4시간 후 이게 되면 성공)

- [ ] **시스템 프롬프트 팩 2종 이상**을 완성했다. 각 팩에 **① 구조화된 출력 형식 ② few-shot 예시 1개 이상 ③ 검증 규칙**이 모두 있다.
- [ ] **멀티턴 대본**이 있다. 최소 **4턴**(세팅→데이터 주입→초안→검증/수정)의 실제 대화가 캡처로 남아있다.
- [ ] **검증 로그**가 있다. AI가 쓴 **핵심 숫자 6개**(총매출·주문건수·AOV·전주대비·취소율·평균별점)를 파이썬 값과 대조해 **통과/불통과**를 기록했다.
- [ ] 전처리를 거친 데이터로 리포트를 만들었다(취소 제거·결측 보정이 숫자에 반영됨).
- [ ] **통합 리포트 1장**이 있다(매출 + 리뷰 + KPI를 한 문서로).
- [ ] 같은 팩을 **다른 챗**에 넣어도 형식이 유지됨을 1개 이상 캡처로 확인했다(재사용성 증거).

> 💡 관찰 가능 기준의 핵심: **"팩을 처음 보는 동료가 그대로 복붙해도 같은 형식의 리포트가 나온다."**

### Step 0 — 준비·데이터 전처리 이해 (45분)

**무엇을/왜.** B의 데이터는 **지저분**합니다. AI에게 요약을 시키기 전에, **무엇이 어떻게 정제됐는지**를 알아야 검증할 수 있습니다.

**어떻게.**
```python
# Colab에서:
!python solution_data_prep.py
```
출력의 **STEP 1(전처리 로그)** 를 반드시 읽으세요. 아래가 나옵니다(샘플 기준, 항상 동일).

```
- 원본 행 수: 503
- 취소주문 제거: 25
- 카테고리 결측 보정('미분류'): 16
- 정제 후 행 수: 478
- 취소율(%): 5.0
```

**설계 판단 포인트(생각해볼 것).**
- 취소주문을 매출에서 **빼는 게 맞나?** (맞습니다. 취소는 실현 매출이 아님) → 리포트에 "취소율 5.0%"를 별도로 노출.
- 카테고리 결측을 **드롭할까 '미분류'로 채울까?** (채움 — 매출 총액을 보존하려고. 대신 '미분류'를 리포트에 표시.)

> 🔎 **검증 문화:** 스크립트 **STEP 5(검증 로그 기준값)** 에 6개 정답 숫자가 나옵니다. **캡처해 두세요.** Step 3에서 AI 리포트와 대조할 '정답지'입니다.

### Step 1 — 프롬프트 팩 설계 (2~3종) (65분)

**무엇을/왜.** 상황이 다르면(매출/리뷰/KPI) **좋은 프롬프트도 달라야** 합니다. 각 상황에 맞는 시스템 프롬프트를 **팩**으로 만듭니다. 이게 B의 핵심 산출물입니다.

**어떻게.** `prompts/` 의 세 팩을 열어 **여러분 손으로 완성**합니다.

| 파일                          | 무엇용    | 여러분이 반드시 채울 것                                   |
| --------------------------- | ------ | ----------------------------------------------- |
| `01_pack_sales_report.md`   | 매출 리포트 | 회사 맥락 · **few-shot 예시 1개** · 검증 규칙              |
| `02_pack_review_summary.md` | 리뷰 요약  | 라벨 정의(긍/부정·주제) · **few-shot** · "리뷰 문장 지어내기 금지" |
| `03_pack_weekly_kpi.md`     | 주간 KPI | KPI 정의 · **few-shot** · "계산식 노출" 규칙             |

**각 팩에 반드시 들어갈 3요소 (D3):**
```
① 구조화 — 출력의 제목·순서를 고정 (예: ■핵심 → ■표 → ■제안)
② few-shot — '이렇게 답해라'의 짧은 정답 예시 1개 (입력 예 → 출력 예)
③ 검증 규칙 — "내가 준 숫자만", "없는 값은 '데이터에 없음'", "계산식 표시"
```

**최소 2종은 완성하세요(3종이면 만점).** 최소 한 팩에는 **few-shot 예시를 여러분이 직접 작성**해야 합니다(제공 예시 복붙만으로는 설계 실습이 안 됩니다).

> 🧪 **설계 판단:** 리뷰 팩은 왜 매출 팩과 달라야 할까요? (리뷰는 숫자보다 **주제 분류**가 핵심 → few-shot으로 "배송/품질/사이즈" 같은 라벨을 가르쳐야 함) 이런 판단을 팩 상단 '설계 메모'에 1~2줄 남기세요.

### Step 2 — 멀티턴 대본으로 리포트 생성 (60분)

**무엇을/왜.** 좋은 리포트는 한 방에 안 나옵니다. **정해진 순서의 대화(대본)** 로 안정적으로 뽑습니다(D4).

**어떻게.** `prompts/04_multiturn_script.md` 의 대본을 따라, **팩마다 하나씩** 리포트를 생성합니다.

```
대본 골격 (팩마다 반복)
턴1  시스템 프롬프트(팩) 주입        → AI가 역할 수락
턴2  [데이터 요약 블록] 주입 + 생성 요청 → 리포트 초안
턴3  형식·톤 교정 ("제안을 행동으로")  → 초안 v2
턴4  자기검증 요청 ("숫자를 대조해줘") → 검증 표
(필요시) 턴5 틀린 숫자 수정
```

`solution_data_prep.py` 출력의 **STEP 4(붙여넣기 블록 A/B/C)** 를 각 팩의 데이터로 사용합니다.

> 🧪 **여기서 캡처!** 최소 한 팩에 대해 **4턴 전체**를 캡처하세요(성공 기준 직결).
> 💡 **컨텍스트 관리(D4):** 대화가 길어져 AI가 형식을 잊으면, 팩을 **다시 한 번 붙여** 되새김질시키세요.

### Step 3 — 검증 로그 (숫자 대조) (35분)

**무엇을/왜.** B의 차별점: 검증을 **로그(기록)** 로 남깁니다. "검증했다"가 아니라 **"무엇을 어떻게 대조해 통과했다"** 를 증명합니다.

**어떻게.** 스크립트 STEP 5의 정답 숫자와 AI 리포트를 대조해 아래를 채웁니다.

```text
검증 로그  | 작성자: [[이름]] | 날짜: 2026-07-13 | 데이터: 지난주(2026-07-06~12)

| # | 항목            | 파이썬(정답)   | AI 리포트 값 | 일치 | 조치            |
|---|----------------|--------------|------------|-----|-----------------|
| 1 | 총매출          | 25,160,000원  |            | O/X | (X면 재생성)     |
| 2 | 주문건수        | 250건         |            | O/X |                 |
| 3 | 평균 객단가(AOV) | 100,640원     |            | O/X |                 |
| 4 | 전주 대비 매출   | +6.7%         |            | O/X |                 |
| 5 | 취소율          | 5.0%          |            | O/X |                 |
| 6 | 평균 별점        | 4.04점        |            | O/X |                 |

판정: 6/6 일치 → 통과 · 하나라도 X → 수정 후 재검증
발견한 할루시네이션: [[AI가 지어낸 숫자·문장이 있었다면 여기 기록]]
```

> 🔎 **여기가 5주차의 절정입니다.** AI가 매출을 25,160,000원이 아니라 25,200,000원처럼 **반올림·왜곡**하는지 눈으로 잡아냅니다.
> ⚠️ **AOV·전주대비**처럼 계산이 들어간 값에서 AI가 자주 틀립니다. 스크립트 값이 **진실**입니다.

### Step 4 — 팩 리팩터링·통합·제출 (25분)

**무엇을/왜.** 검증에서 드러난 약점으로 **팩을 개선**합니다(이게 '재사용 자산'을 완성하는 단계).

**어떻게.**
1. 검증에서 AI가 틀린 부분이 있으면, 해당 팩의 **검증 규칙을 강화**합니다. 예: *"AOV는 반드시 총매출/주문건수 계산식을 함께 보여줘."*
2. 세 리포트를 **한 문서**로 통합합니다.

```
[통합 주간 리포트]
1) 매출 요약 (팩①)   2) 고객 리뷰 요약 (팩②)   3) 주간 KPI (팩③)
[부록] 프롬프트 팩 전문 · 멀티턴 대본 · 검증 로그 · 데이터 출처
```

> 🎯 개선된 팩 + 대본 + 검증 로그 = **다음 주에 그대로 재사용 가능한 시스템**. 이게 B의 완성입니다.

## 7. 자주 막히는 지점 & 해결 (FAQ / 트러블슈팅)

**Q1. few-shot 예시를 어떻게 만들죠?**
A. "입력 예 → 이상적인 출력 예"를 **짧게 1쌍** 적으면 됩니다. 예: `입력: 토 매출 564만(최고) / 출력: "■핵심: 토요일이 주간 피크(564만원)…"`. 완벽한 예보다 **형식을 보여주는** 예가 중요합니다.

**Q2. 멀티턴이 길어지니 AI가 형식을 잊어요.**
A. 컨텍스트 한계입니다(D4). **팩(시스템 프롬프트)을 다시 붙여** 상기시키거나, 새 대화를 열고 팩+데이터를 한 번에 넣으세요.

**Q3. AI가 취소주문을 포함해서 매출을 부풀렸어요.**
A. 데이터 주입 시 **"이 숫자는 취소 제외·정제 완료본"** 이라고 명시하세요. 그래도 AI가 임의로 더하면 검증 로그에서 X로 잡고, 팩 규칙에 *"주어진 합계를 재계산하지 말 것"* 을 추가하세요.

**Q4. 리뷰 요약에서 AI가 없는 리뷰 문장을 지어내요.**
A. 리뷰 팩의 검증 규칙에 *"내가 준 샘플 리뷰만 인용. 새 문장 창작 금지"* 를 넣고, 요약은 **별점 분포·주제 빈도** 중심으로 시키세요.

**Q5. AOV·증감률을 AI가 자꾸 틀려요.**
A. LLM은 계산에 약합니다(D1). **파이썬이 계산한 값(100,640원, +6.7%)을 데이터에 함께 주고**, 팩 규칙에 *"주어진 계산값을 그대로 사용, 재계산 금지"* 를 넣으세요. 검증 로그로 최종 확인.

**Q6. 팩 2종을 못 채웠어요(시간 부족).**
A. **1종을 완성도 높게** 마치는 게 3종을 어설프게 만드는 것보다 낫습니다. 매출 팩(①)을 구조화·few-shot·검증까지 완성하고, 멀티턴+검증 로그를 붙이면 핵심은 충족됩니다.
