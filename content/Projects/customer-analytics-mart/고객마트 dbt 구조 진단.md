이 글은 프로시저를 dbt로 옮기며 폴더 구조부터 매크로까지 실제로 어떤 판단을 내렸는지 코드로 짚은 기록입니다.

## 폴더는 레이어가 아니라 프로시저 기준으로 나눴다

이관 당시 모델 폴더는 이렇게 생겼습니다.

```text
models/
├── sources/                   # 소스 선언 yml만 (등록 6개)
├── source_view/               # 1개 — 최신 스냅샷 필터 + 타입 캐스팅
├── subtable/                  # 42개 — 부품 모델
├── pom_procedure/             # 18개 — 프로시저 단계 체인 + 최종 마트
├── dentalMaturity_DashBoard/  # 1개 — 대시보드용
└── testfile/                  # 2개 — 실험용 스크래치
```

dbt 관례인 staging / intermediate / marts 구분 대신 원본 프로시저 단위(부품 / 조립)로 나눴습니다. 레이어 정보는 파일명 접두사에 넣었습니다 — `POMSUB_`가 붙으면 중간 산출물, `_TMP`가 붙으면 프로시저의 한 단계입니다. 원본 구조를 그대로 반영해야 원본 프로시저와 1:1 대조가 되니, 이관 초기엔 이쪽이 더 안전한 선택이었습니다. 대가는 하나입니다. `dbt build --select path:models/staging` 같은 레이어 단위 실행은 안 됩니다(접두사로는 되지만 폴더 경계와 안 맞습니다). 의존 방향은 `subtable → pom_procedure` 한 방향으로 지켰고 거꾸로 가는 참조는 0건이라, 나뉘어 있지 않은 건 폴더였지 흐름은 아니었습니다.

## 이름을 바꿔도 물리 테이블은 그대로 둘 수 있다

원본 프로시저의 테이블명을 dbt 모델명으로 그대로 가져왔다고 앞서 적었는데, 그렇다고 나중에 더 나은 이름으로 못 바꾸는 건 아닙니다. dbt 모델의 파일명(로직상 이름)과 실제 DB에 만들어지는 물리 테이블명은 기본적으로 같지만, `config(alias=...)`로 둘을 분리할 수 있습니다.

```sql
{{ config(
    materialized='table',
    alias='RECENT_POLICYNO'    -- DB에는 이 이름으로 그대로 생성됨
) }}

SELECT ...
```

파일명은 `recent_policy.sql`처럼 dbt 컨벤션에 맞게 새로 지어도, `alias`로 원래 물리 테이블명(`RECENT_POLICYNO`)을 고정하면 DB 안의 실제 테이블 이름은 안 바뀝니다. BI 대시보드가 그 테이블을 직접 조회하고 있어도, 외부 배치가 하드코딩된 테이블명을 쓰고 있어도, Dagster asset이 그 물리명을 기준으로 잡혀 있어도 전부 영향받지 않습니다. 원본 이름을 그대로 쓰는 것과 나중에 dbt 컨벤션으로 정리하는 것 사이엔 실제로 충돌이 없다는 뜻입니다. 파일명은 얼마든지 바꾸고, `alias`만 원래 이름으로 고정하면 됩니다.

## 프로시저 흔적은 일부러 남겼다

모델 파일 대부분에 프로시저 시절 흔적을 의도적으로 남겼습니다. 작성자·작성일 헤더 주석, `기존 테이블명 / 신규 테이블명` 대응 주석, 주석 처리된 `-- DROP TABLE IF EXISTS`와 `-- INTO ##TEMP_*`(10개 파일), 하드코딩 테이블명을 주석으로 남기고 그 아래를 `ref()`로 바꾼 자리 같은 것들입니다.

```sql
-- 기존 테이블명: dbo.RECENT_POLICYNO  /  신규: recent_policy
-- SELECT ... INTO ##TEMP_RECENT_POLICY        (원본 단계, 주석으로 보존)
SELECT c.CustomerKey, MAX(p.PolicyNo) AS RecentPolicyNo
FROM {{ source('dw', 'PolicyLatest') }} p
JOIN {{ ref('valid_customer') }} c            -- 원래는 dbo.VALID_CUSTOMER 하드코딩
  ON c.CustomerKey = p.CustomerKey
GROUP BY c.CustomerKey
```

정리 안 된 잔재처럼 보이지만 목적이 있었습니다. 금융권에서 프로시저를 다른 도구로 옮기면 원본과 1:1로 대조하는 검증을 요구받는 경우가 많고, 이 주석들이 그 대조표 역할을 합니다. 원본 프로시저 폐기가 승인되기 전까지는 지우지 않기로 했습니다.

## 파라미터 배선이 코드 밖에 있던 지점들

일부 로직은 dbt 코드만 봐서는 완결돼 보이지 않습니다. 나머지 절반이 Dagster 쪽에 있었기 때문입니다.

청약 주차별 캠페인 타겟 모델이 그렇습니다. 청약일을 W-5(당월)부터 W-1(4주 뒤)까지 주차로 나누는 규칙은 원래 원본 프로시저가 날짜 파라미터를 받아 계산했습니다. dbt로 옮기면서 그 계산을 SQL 밖으로 뺐습니다. 모델은 파라미터 자리만 갖고, 실제 날짜 값은 Dagster asset이 계산해서 넘깁니다 — `-- depends_on: {{ source('dagster', ...) }}` 주석이 그 배선을 보여줍니다([[고객마트 Dagster 통합]]). 날짜 계산 로직을 SQL에 하드코딩하지 않고 오케스트레이션 레이어로 넘긴 덕분에, 캠페인마다 달라지는 주차 기준을 모델 코드 수정 없이 바꿀 수 있습니다.

`campmonth`도 비슷한 성격입니다. 원장 데이터가 기간계(링크드 서버로 붙는 실시간 원장)와 정보계(월별 스냅샷 DM) 두 곳에서 왔는데, 기간계는 스냅샷 키가 없어 "현재 상태"만 존재합니다. 그래서 기간계를 직접 읽는 모델은 `campmonth`로 과거 시점을 재현하지 못합니다 — 이건 배선 미완이 아니라 소스 자체의 한계입니다. `campmonth`의 실제 역할은 계약 경과월을 계산해 휴지기 대상자를 걸러내는 것이었지, 시점 재현이 아니었습니다.

## SQL 습관

SQL은 프로시저 스타일을 상당 부분 그대로 가져왔습니다. CTE를 쓴 모델이 64개 중 12개이고 나머지는 중첩 서브쿼리입니다. 가장 깊은 건 3중 중첩에 `WHERE 1=1` 스캐폴딩이 남은 201줄짜리 허브 모델입니다. 모든 조인에 `WITH(NOLOCK)`을 붙였는데, 원장 부하를 피하려는 의도였습니다(dirty read를 허용하는 트레이드오프이긴 합니다).

**incremental 없음.** 51개 모델이 매번 전체 재생성이고, 대신 모든 모델에 `GETDATE() AS ETLDATE`를 심어 나중에 워터마크로 전환할 여지는 남겨뒀습니다. 기간계 데이터를 Debezium 등을 통해 증분 모델로 만들 수 있는 기회가 있었다면 많은 것을 배웠을 것 같습니다.

문서는 64개 중 12개에 있었는데, 있는 곳의 내용은 밀도가 높습니다. 청구 플래그 판정 임계값, 정책 변경 이력(날짜와 사유), 상태코드 전수 같은 코드만 읽어서는 복원 안 되는 도메인 지식이 `schema.yml`에 적혀 있었습니다.

매크로 2개도 각각 목적이 뚜렷했습니다. `add_month`는 반환 길이(6자리/8자리)를 파라미터로 받게 설계해서 호출부가 필요한 자릿수를 고를 수 있게 했습니다. 동적 기준월 조회 매크로는 스냅샷 테이블의 최신 월을 `run_query`로 가져와 기본값으로 씁니다. 프로시저마다 반복되던 "캠페인월 ±N개월" 계산을 매크로 하나로 뽑아 25곳에서 재사용한 것도 같은 맥락입니다 — 계산 규칙이 하나 바뀌면 매크로 한 곳만 고치면 됩니다.

## 남긴 판단들

프로시저 이관이라는 제약 안에서 여러 판단을 내렸습니다. `#temp`를 물리 테이블로 승격하지 않고 ephemeral로 옮긴 것, 그레인·역할·캠페인 세 축의 태그로 실행 단위를 잡은 것, `campmonth`를 vars로 뺀 것, 최상류 소스에 freshness를 건 것, 구/신 테이블명 주석으로 이관 추적성을 남긴 것, group + owner로 소유권을 정의한 것, 하드코딩 테이블명을 `ref()`/`source()`로 바꾼 것(111곳). 표준 구조를 그대로 따르지 않았다고 낮게 볼 일은 아닙니다 — 원본과의 대조 가능성을 지키면서 옮기는 게 우선순위였고, 그 안에서는 맞는 선택들이었습니다.
