[[Projects/customer-analytics-mart/index|프로젝트 개요]]로 돌아가기

"stg / intermediate / mart로 잘 나뉘어 있는가"라는 질문에서 출발했습니다. 답부터 말하면 **레이어 개념이 없는 게 아니라 dbt 관례가 아닌 자체 규약으로 표현되어 있었습니다.** 레이어 정보가 폴더가 아니라 파일명 접두사(`POMSUB_` = 중간 산출물, `*_TMP*` = 프로시저 단계)에 인코딩되어 있습니다. 문제는 그 규약이 폴더 경계와 일치하지 않아 `dbt build --select path:` 같은 레이어 단위 실행이 불가능하다는 점입니다.

## 폴더별 실질 레이어 판정

| 폴더 | 모델 수 | 실질 레이어 | 판정 근거 |
|---|---|---|---|
| `sources/` | 0 (yml만) | source 계약 | 등록 소스 6개 — 실제 참조되는 외부 테이블 대비 커버리지 약 6% |
| `source_view/` | 1 | staging | 최신 스냅샷 필터 + 타입 캐스팅. 전형적 staging인데 소스로도 이중 등록된 모순이 있습니다 (아래) |
| `subtable/` | 42 | staging + intermediate + mart 혼재 | 원장 1:1 추출(스테이징 성격) ~8개, 고객 그레인 집계 ~26개, 대시보드·타겟 산출물 ~8개가 한 폴더에 |
| `pom_procedure/` | 18 | intermediate 체인 + mart 종단 | 와이드 베이스 → 프로시저 단계 체인(ephemeral 7개) → 최종 마트 4개의 3단 구조 |
| `dentalMaturity_DashBoard/` | 1 | mart | 단, `#temp` 테이블이 남아 있어 실행 자체가 불가능한 상태 |
| `testfile/` | 2 | — | 스크래치 파일이 프로덕션 경로에 상주. 미정의 var 참조로 빌드를 깨뜨림 |

계층 "방향"은 건전합니다. subtable → pom_procedure 단방향이고 역류가 0건입니다. 나뉘어 있지 않은 건 폴더이지 흐름이 아니었습니다.

## 프로시저 이관 흔적 — 지배적 패턴

코드 전반이 T-SQL 스토어드 프로시저 이관 중임을 증언합니다.

- 프로시저 헤더 템플릿(작성자/작성일/메모)이 대부분의 모델에 그대로 잔존
- `기존 테이블명 / 신규 테이블명` 주석으로 이관 전후 대응 기록
- 주석 처리된 `-- DROP TABLE IF EXISTS`, `-- INTO ##TEMP_*` DDL (10개 파일)
- `@campmonth` 프로시저 변수 주석 바로 아래 `{{ add_month() }}` 매크로로 대체한 흔적
- 하드코딩 테이블명을 주석 처리하고 `ref()`로 교체한 전환 패턴 (올바른 방법론이 이미 코드 안에 있습니다)

이 흔적들은 정리 안 된 잔재인 동시에 감사 가능한 이관 로그입니다. 금융권 이관은 원본 프로시저와의 1:1 대조 검증이 요건인 경우가 많아서, 주석 정리는 원본 폐기 승인 이후로 미루는 게 맞습니다.

## 치명 이슈 — 빌드가 안 되는 이유

### dbt_project.yml이 유효한 YAML이 아니다

```yaml
models:
  my_dbt_project:
    +pre-hook:            # 매핑 키
      - "INSERT INTO dbt_model_logs ..."
    - subtable:           # 같은 레벨에 시퀀스 항목 — 파싱 불가
        +materialized: table
```

동일 들여쓰기에서 매핑 키와 시퀀스 항목(`- subtable:`)을 섞을 수 없습니다. 파일 수정 시각이 마지막 정상 manifest 생성 10분 뒤라서, **마지막 성공 빌드 직후 이 파일을 편집하다 깨진 채 남은 것**으로 보입니다.

참고로 이 프로젝트는 이전 직장의 DB를 대상으로 했기 때문에 지금은 어차피 실행 환경이 없습니다. 그래도 이 오류는 짚을 가치가 있습니다 — `dbt parse`는 DB 연결 이전에 이 파일부터 읽으므로, YAML 파손은 DB 부재와 무관하게 첫 단계에서 걸립니다 (PyYAML로 직접 재현 확인). 포트폴리오용으로 로컬 DB(DuckDB 등)에 재현하려 해도 이 수정이 첫 단추입니다.

부수 효과 둘. 첫째, 폴더별 `+materialized` 기본값이 무력화됐습니다 (실제로는 62/64 모델이 인라인 `{{ config() }}`로 중복 선언하고 있어 실피해는 2개 모델에 국한). 둘째, 모델 실행시간을 기록하려던 pre/post-hook은 **한 번도 적용된 적이 없습니다** — 마지막 정상 manifest에서 64개 모델 전부 hook이 비어 있었습니다.

### packages.yml이 없다

`dbt_utils`, `dbt_expectations`가 설치되어 있고 schema.yml이 `dbt_utils.unique_combination_of_columns`를 실제로 쓰는데 의존성 선언 파일이 없습니다. `dbt_packages/`는 gitignore 대상이라 신규 클론에서는 `dbt deps`를 실행할 근거조차 없이 테스트가 깨집니다. 재현 가능한 빌드가 성립하지 않습니다.

### 자격증명이 저장소 경로에 있다

`profiles.yml`이 프로젝트 루트에 평문 자격증명을 담은 채 존재하고 `.gitignore`에 없습니다. 이 repo를 어디든 push하는 순간 유출입니다. (조치: `~/.dbt/` 이동 + env_var 치환 + gitignore 등록 + 자격증명 로테이션. 실제 운영은 홈 디렉토리 프로파일로 돌았을 가능성이 로그에 있어 루트 파일은 잔재 삭제가 정답일 수 있습니다.)

## 논리 결함 — 조용히 틀린 결과를 내는 코드

**BB 타겟 모델은 파라미터 배선이 안 끝난 이관 중간 산출물입니다.** 청약일 주차별로 W-5(당월)~W-1(4주뒤)을 나누는 룰 설계 자체는 타당하고, 운영은 날짜 파라미터를 받는 원본 SP가 담당했습니다. 문제는 이 dbt 파일에서 그 파라미터(`@AcquisitionDateFrom5` 등) 자리에 자리표시자 정수 `5`, `4`, `3`...이 남아 있다는 점입니다. 좌변이 `YYYYMMDD` 8자리 날짜 문자열이라 varchar↔int 암묵 변환 후 `20240315 BETWEEN 5 AND 5`는 항상 거짓 — 이 파일을 그대로 실행하면 주차 분류 전체가 에러 없이 NULL로 떨어집니다. 같은 파일의 `-- depends_on: {{ source('dagster','bb_auto_var') }}` 주석이 설계 의도를 보여줍니다: Dagster에서 주차별 날짜를 주입하려 했고 그 통합이 미완 TODO로 남으면서 배선이 끊긴 것입니다 ([[고객마트 Dagster 통합]] 참조).

**치과 만기 대시보드 모델은 실행이 원천 불가능합니다.** `DROP TABLE #...`, `SELECT ... INTO #temp`가 그대로 남아 있는데 materialization은 `view`로 떨어집니다. 프로시저 문법이 dbt 래핑과 충돌하는 전형적인 이관 미완 사례입니다.

**모델이자 소스인 이중 정의.** staging 뷰 하나가 모델로도 존재하고 `sources.yml`에 소스로도 등록되어 있습니다. 소비자들은 `source()`로 참조하므로 dbt는 모델 → 소비자 의존성을 인식하지 못합니다. 병렬 실행 시 갱신 전 데이터로 하위 마트가 만들어질 수 있습니다.

**`campmonth`로 과거 시점을 재현하려 하면 기간계 직접 참조 구간에는 닿지 않습니다.** `campmonth`의 본래 역할은 계약 경과월 계산(`POMSUB_REST_PERIOD` 등)을 통한 휴지기 대상자 제외이지 시점 재현이 아닙니다. 그런데 허브 모델(`POMSUB_CUSTOMER_POL_BASE`)을 포함해 원장(기간계, `[MIS].ACEINA` 링크드 서버)의 계약·특약·동의·블랙리스트 뷰를 직접 참조하는 subtable 12개 중 11개는 코드 어디에도 `campmonth`가 등장하지 않습니다. 기간계 자체가 월별 스냅샷 키 없이 "현재 상태"만 담는 실시간 원장이라 걸 수 있는 날짜 컬럼이 애초에 없습니다. 그 결과 다른 `campmonth`로 실행해도 고객·계약 모집단은 항상 실행 시점의 현재 상태로 고정되고, `add_month()`로 계산되는 날짜 파생 컬럼만 해당 월인 것처럼 계산됩니다 — 에러 없이 시점이 어긋난 결과가 조용히 나옵니다. 대조군인 `GDMS_DM`은 `baseym` 스냅샷 키가 있어 정보계에 가깝고, 이쪽은 최신월만 쓰고 있을 뿐 필터링 자체는 가능한 구조입니다.

## SQL 품질

- CTE 사용률 19% (12/64). 나머지는 중첩 서브쿼리 — 최악은 3중 중첩 + 의미 없는 `WHERE 1=1` 스캐폴딩이 남은 201줄짜리 허브 모델
- `SELECT *` 13곳. 특히 최상류 staging 모델이 `SELECT cast(...) as ETLDate_datetime, *`라서 동일 개념 컬럼이 2개 생기고 원천 스키마 변경이 하위 전체로 무통보 전파됩니다
- 하드코딩 3/4-part 테이블명 98곳 — [[고객마트 리니지 분석]]에서 정량으로 다룸
- 모든 조인에 `WITH(NOLOCK)` — 원장 부하 회피 의도는 이해되지만 dirty read를 허용합니다. 청구금액·계약상태 기반 캠페인 타겟 산출이라는 맥락에선 감사 추적 리스크입니다. `READ COMMITTED SNAPSHOT` 전환이 정석
- incremental 전략 전무. 51개 모델이 매 실행 전체 재생성이고 2022년 12월부터 매번 전체 재계산하는 모델도 있습니다. 모든 모델에 `GETDATE() AS ETLDATE`를 이미 심어놔서 워터마크 인프라는 갖춰져 있는데 쓰지 않습니다

## 테스트와 문서화

테스트 노드는 4개인데 실질 커버리지는 64개 모델 중 1개(1.6%)입니다. 나머지 3개는 tests/ 폴더의 매크로 확인용 스크래치 쿼리 — singular test는 0행 반환이 통과 조건인데 항상 1행을 반환하도록 짜여 있어 설계상 영구 실패합니다. 그중 1개는 존재하지 않는 매크로를 호출해 `dbt test` 전체를 컴파일 단계에서 중단시킵니다. 그레인 키(`unique` + `not_null`) 검증이 하나도 없다는 게 가장 아픕니다.

문서화는 12/64로 커버리지는 낮지만 품질이 다릅니다. 청구 플래그의 판정 임계값, 정책 변경 이력(날짜와 사유), 상태코드 목록 전수 열거 — 코드만 읽어서는 복원할 수 없는 도메인 지식이 schema.yml에 들어 있습니다. 문제는 품질이 아니라 커버리지입니다.

매크로 2개도 의도는 정확했습니다. 다만 `add_month`는 첫 번째 파라미터(반환 길이)가 본문에서 아예 쓰이지 않는데 모든 호출부가 6이나 8을 전달합니다 — 호출자는 반환 길이를 제어한다고 믿지만 실제로는 항상 6자리입니다. 호출부마다 `SUBSTRING`으로 좌변을 절단하는 방어 코드가 붙은 이유입니다. 동적 기준월 조회 매크로는 `{% if execute %}` 가드가 없어 컴파일에도 DB 연결이 필요하고 결과가 비면 미정의 변수 에러가 납니다.

## 잘한 점

균형을 위해 명시합니다. 이 프로젝트가 표준 구조가 아니라는 이유로 저평가되기 쉽지만 레거시 프로시저 이관으로 보면 수준 있는 판단이 여럿 쌓여 있습니다.

1. **ephemeral의 정확한 활용** — 프로시저 `#temp`를 물리 테이블로 무지성 승격하지 않고 ephemeral(CTE 인라인)로 매핑했습니다. materialization 트레이드오프를 이해해야 나오는 선택입니다. 많은 이관 프로젝트가 여기서 실패합니다.
2. **태그 기반 실행 제어** — 그레인 축(고객/증권/피보험자 단위) × 역할 축(모수/제외조건) × 캠페인 축의 직교 태그를 58개 모델에 부여. 월간 배치 운영 현실에 맞는 설계입니다.
3. **프로시저 파라미터 → vars 승격** — `campmonth`는 계약 경과월을 계산해 휴지기(재접촉 유예) 대상자를 걸러내는 캠페인 핵심 파라미터입니다. 하드코딩에서 `vars`로 빠져나와 매월 값만 바꿔 재사용할 수 있게 됐습니다. 다만 이 값으로 과거 시점을 재현하려 하면 기간계를 직접 참조하는 구간까지는 닿지 않습니다(아래 논리 결함 참조).
4. **이관 추적성** — 구/신 테이블명 대응 주석은 감사 대조표 역할을 합니다.
5. **도메인 문서의 밀도** — 위에 쓴 대로입니다.
6. **소스 freshness 계약** — 최상류 소스에 `loaded_at_field` + warn 1일/error 5일을 정확히 걸었습니다.
7. **model governance 채택** — groups + owner 정의는 dbt 1.5+ 기능을 따라간 흔적입니다.
8. **ref() 전환 진행 중** — 111곳의 ref/source와 깊이 9의 DAG는 적은 양이 아닙니다. 방법론은 이미 팀 안에 있고 남은 98곳에 같은 패턴을 적용하면 됩니다.
