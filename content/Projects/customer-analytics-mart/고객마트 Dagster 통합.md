[[Projects/customer-analytics-mart/index|프로젝트 개요]]로 돌아가기

오케스트레이션 도구를 고를 때 제약이 두 개 있었습니다. 실행 환경이 Windows(Hyper-V 불가)라는 것, 그리고 이미 dbt로 변환 레이어를 짜고 있었다는 것. Airflow는 Windows 네이티브 구동이 사실상 불가능했고 Dagster는 순수 Python이라 바로 돌았습니다. 하지만 결정적 이유는 환경이 아니라 워크플로우 모델이었습니다.

## 어떤 환경이었나

보험사는 다른 금융회사들처럼 보안 규정이 까다롭습니다. 당시 재직했던 회사는 폐쇄망에서 DB를 운영했습니다. DB에 접근하려면 전산센터 단말기로 가상 윈도우에 붙고, 거기서 데이터를 추출해야 했습니다.

폐쇄망이라 파이썬 라이브러리 하나 설치하는 것도 일이었습니다. 노트북에서 라이브러리를 받아 물리적으로 옮겨야 했고, 환경 설정에 상당한 시간이 들었습니다. 금융업계 특성상 USB 사용도 불가능했습니다.

SSIS 같은 배치 시스템도 없었습니다. 그래서 초기에는 파이썬 스크립트를 윈도우 작업 스케줄러에 걸었고, 나중에 APScheduler 라이브러리로 옮겼습니다. 실행 이력이 로그 파일에만 남아서, 어느 스크립트가 언제 실패했는지 확인하려면 파일을 뒤져야 했습니다.

Airflow로 운용하고 싶었지만 할당된 자원은 단말기 위의 가상 윈도우뿐이었습니다. 가상환경 위에 또 가상환경을 올리는 건 불가능했고(Hyper-V 차단), 별도 리눅스 리소스를 받는 것도 어려웠습니다. 인터넷이 안 되니 도커 설치부터 막힙니다.

UI로 배치를 관리하는 건 포기했다고 생각하던 시점에 찾은 것이 Dagster였습니다. `pip install dagster dagster-webserver` 후 `dagster dev` 한 줄로 웹 UI가 뜹니다. 도커도, 별도 리눅스 인스턴스도, 하이퍼바이저도 필요 없습니다. 이 환경에서는 선택지가 사실상 Dagster뿐이었다고 보는 게 맞습니다.

다만 환경 제약은 진입 조건이었을 뿐이고, 계속 쓰기로 한 이유는 아래의 워크플로우 모델입니다.

## Task 중심 vs Asset 중심

Airflow류는 "무엇을 실행할지"(task)를 나열하고 Dagster는 "무엇이 만들어지는지"(asset)를 선언합니다. dbt의 모델 개념이 정확히 후자입니다 — 모델 하나가 테이블 하나이고 `ref()`가 계보를 만듭니다. 개념 자체는 [[Dagster의 자산 중심 워크플로우]]와 [[Airflow 3와 Dagster 비교]]에 따로 정리했습니다.

Dagster는 dbt 모델을 asset으로 그대로 흡수합니다. dbt의 리니지가 Dagster asset 그래프에 그대로 나타나고 dbt의 `group`/`tags`가 Dagster UI 그룹 뷰로 이어집니다. 이 프로젝트에서 체감한 시너지는 네 가지였습니다.

1. 테이블 단위 상태 추적 — 어떤 마트가 언제 갱신됐는지가 1급 정보
2. 리니지 가시성 — 장애 시 역추적이 그래프 클릭으로 끝남
3. 품질 이슈 대응 — 문제 asset과 그 하류만 특정 가능
4. 선택적 재실행 — 변경된 자산만 다시 materialize

트레이드오프도 있었습니다. 러닝커브가 있고 Airflow 대비 커뮤니티와 한국어 자료가 적습니다. 개념(asset, materialization, partition)이 낯설어 초기 진입이 느립니다.

## dbt 실전 기능 5종 — 설계와 실제

프로젝트에서 활용하려던 dbt 기능과 [[고객마트 dbt 구조 진단]]에서 드러난 실제 상태를 대조하면 이렇습니다. 각 기능의 문법과 설정 예시는 [[dbt 실전 기능 5종 정리]]에 따로 정리했습니다.

| 기능 | 설계 의도 | 실제 상태 |
|---|---|---|
| Source Freshness | 최상류 스냅샷 뷰에 `loaded_at_field` + warn 1일/error 5일 | 정확히 동작하는 모범 사례. 단 6개 소스 중 1개에만 적용 |
| pre/post Hook | 모델별 실행 시작·종료 시간을 로그 테이블에 기록 → 쿼리 튜닝 근거 | 설정 파일 YAML 파손으로 **한 번도 적용된 적 없음**. dbt가 이미 남기는 run_results.json과 기능 중복이기도 함 |
| Macro | 캠페인월 ±N개월 계산, 스냅샷 최신 기준월 동적 조회 (`run_query`) | 25곳에서 실사용, 프로시저 반복 코드를 실제로 압축. 파라미터 계약 결함은 진단 문서 참조 |
| Test | 복합키 정합성 (`dbt_utils.unique_combination_of_columns`) | 정상 동작 1건이 전부. 나머지는 스크래치 |
| Docs | schema.yml에 group·모델·컬럼 설명 | 12/64 커버리지, 품질은 상급 (판정 임계값·정책 변경 이력까지 기록) |

"기능을 아는 것"과 "프로젝트 전반에 계약으로 정착시키는 것" 사이의 간극이 이 표에 그대로 있습니다. freshness도 hook도 테스트도 첫 사례는 정확했는데 전파가 안 됐습니다.

## 남은 과제 (당시 TODO 기준)

미완으로 남은 것들:

- Dagster asset을 dbt source로 등록해 모델이 의존하게 하기 — BB 타겟 모델에 `-- depends_on: source('dagster', ...)` 주석 흔적만 남아 있습니다
- Dagster에서 dbt asset으로 변수 던지기 — 이게 됐다면 BB 타겟의 파라미터 유실 결함은 없었을 것
- upsert(증분) 전략 — incremental 도입과 같은 과제
- dagster + dlt 연계, 로컬 key-value 스토리지

돌아보면 미완 과제 두 개(변수 주입, asset-source 의존)가 정확히 치명 결함 지점과 겹칩니다. 오케스트레이션 통합이 "있으면 좋은 것"이 아니라 정합성 문제였던 셈입니다.

## 블로그 글감 후보

이 프로젝트에서 나올 수 있는 글을 우선순위순으로 정리했습니다.

1. **SP 하나에 몰아넣던 마트, dbt로 옮기다 만 이야기** — 문제 → 2계층 설계 → 남은 빚. 서사가 이미 갖춰져 있고 실무 배경이 있는 글은 튜토리얼 재탕과 차별화됩니다
2. **Task 중심 vs Asset 중심, 왜 Dagster였나** — Windows 제약이라는 현실적 사유 + 개념 비교. 한국어 자료가 드문 주제
3. **dbt 실전 기능 5종 활용기** — hook 실행시간 로깅, run_query 동적 기준월 매크로는 검색해도 잘 안 나오는 실전 팁
4. **dbt ephemeral의 함정** — ephemeral을 left join에 썼다가 에러를 만나 table로 우회한 경험. 단, "CTE로 감싸면 될 것"이라는 가설이 미검증이라 재현 실험이 선행되어야 함
5. ~~Dagster↔dbt 심화 통합 시리즈~~ — DuckDB 로컬 복원으로 실제 구현. [[고객마트 로컬 복원]] 참조
