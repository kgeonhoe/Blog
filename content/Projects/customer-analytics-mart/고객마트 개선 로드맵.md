[[Projects/customer-analytics-mart/index|프로젝트 개요]]로 돌아가기

[[고객마트 dbt 구조 진단]]과 [[고객마트 리니지 분석]]의 결론을 실행 순서로 옮깁니다. 핵심 원리는 두 가지입니다.

1. **dbt에서 모델의 논리 이름 = 파일명이고 폴더 경로와 무관합니다.** 파일 이동만으로는 `ref()`도 물리 테이블명도 깨지지 않습니다. 폴더 재배치가 완전 무중단인 이유입니다.
2. **이름을 바꿀 때는 `{{ config(alias='기존물리명') }}`으로 물리 테이블명을 고정**하면 BI 대시보드·외부 조회·Dagster 자산이 영향받지 않습니다.

## 레이어 매핑 (현재 → 목표)

```
현재 (도메인 축)                     목표 (레이어 축)
──────────────────                  ──────────────────
sources/       소스 계약 6개    →   staging/       ~9 모델 + 소스 yml (원장/DW/캠페인 소스별 분리)
source_view/   staging 1개     →   intermediate/  ~39 모델 (customer / policy / pom 도메인별)
subtable/      3계층 혼재 42개  →   marts/         ~13 모델 (campaign / pom / refund / dental)
pom_procedure/ int+mart 18개
dentalMaturity/ mart 1개 (실행불가)
testfile/      스크래치 2개    →   삭제
```

배정 기준은 SQL 내용입니다. 원장 1:1 추출(콜에러 정제, 유효계약 고객 등) ~8개가 staging으로, 고객 그레인 집계·룰 계열 ~26개와 허브 + 프로시저 단계 체인 ~13개가 intermediate로, 캠페인 타겟·대시보드·세그먼트 종단 ~13개가 marts로 갑니다. 이름은 `stg_원장__유효계약.sql` 식의 `stg_`/`int_`/`fct_` 규약을 따르되, 물리명은 alias로 고정합니다.

## 단계별 실행

### Phase 0 — 빌드 복구 (반나절, 즉시)

지금은 `dbt parse`조차 안 되므로 다른 모든 논의가 공중에 떠 있습니다.

1. dbt_project.yml의 models 블록 문법 수정 (시퀀스 하이픈 제거 → 중첩 매핑)
2. 미정의 var를 참조하는 스크래치 모델 삭제
3. 미정의 매크로를 호출하는 테스트 파일 삭제
4. 동적 기준월 매크로에 `{% if execute %}` 가드 + 빈 결과 기본값 추가

게이트: `dbt compile` 0 에러.

### Phase 1 — 안전망 (1주)

1. `packages.yml` 작성 (dbt-utils, dbt-expectations) + lock 파일 커밋
2. profiles.yml을 `~/.dbt/`로, 자격증명 로테이션, gitignore 보강
3. **회귀 기준선 확보** — 각 마트의 행수·핵심 컬럼 합계 스냅샷. 이후 모든 단계는 이 기준선과 대조합니다
4. 그레인 키 4곳에 `unique` + `not_null` 테스트 (허브 모델의 증권번호, 고객 통계 모델들의 고객키)
5. schema.yml의 모델명 오타 2건 수정 (문서·테스트가 유실되고 있던 지점)
6. CI: `dbt deps && dbt parse && dbt compile`

게이트: 테스트 통과 + 기준선 확보.

### Phase 2 — 결함 수정 (1~2주)

1. 모델·소스 이중 정의 해소 — 소스 선언을 제거하고 소비자를 `ref()`로 전환. DAG 연결이 목표
2. BB 타겟의 정수 리터럴을 실제 날짜 파라미터로 복원 — **원본 프로시저 대조와 업무 담당자 확인 필수**
3. 치과 만기 모델을 `#temp` 없는 CTE 체인으로 재작성 + `table` 명시
4. add_month 매크로의 무시되는 파라미터 정리 — 25개 호출부의 결과가 바뀔 수 있어 기준선 대조 필수. 리스크가 크면 파라미터 제거 쪽이 안전

게이트: 수정마다 기준선 행수/합계 일치.

### Phase 3 — 폴더 재배치 (1주, 완전 무중단)

1. `git mv`로 파일만 이동. 파일명·모델명 변경 없음
2. 레이어별 기본 설정으로 위임:

```yaml
models:
  my_dbt_project:
    staging:      {+materialized: view, +tags: [staging]}
    intermediate: {+materialized: ephemeral, +tags: [intermediate]}
    marts:        {+materialized: table, +tags: [marts]}
```

3. 모델 내부의 중복 `{{ config(materialized='table') }}` 40여 개 제거
4. schema.yml 레이어별 분할

게이트: `dbt run` 결과가 Phase 2 종료 시점과 동일. 물리 테이블명이 하나도 안 변했으므로 다운스트림 영향 0.

### Phase 4 — 소스 계약 봉합 (2~3주)

하드코딩 98곳을 `source()`로 파일 단위로 쪼개 전환하고 건건이 기준선 대조. 우선순위는 참조 빈도순(원장 계약 뷰 → DW 상품 마스터 → 캠페인 통제 테이블). `sources.yml`의 database/schema를 `env_var()`로 파라미터화해 dev/prod 분리 기반을 만듭니다. 목표: 리니지 고아 21개 → 0개.

### Phase 5 — 네이밍 정규화 (2주, alias로 무중단)

`stg_`/`int_`/`fct_` 파일명 전환 + `config(alias=)`로 물리명 고정. 접두사 오타, 트레일링 언더스코어, 대소문자 혼용을 이때 함께 해소합니다. alias 제거는 다운스트림 마이그레이션이 끝난 뒤 별도 일정으로 진행합니다.

### Phase 6 — 성능·품질 (지속)

- incremental 도입: 2022년부터 전체 재계산하는 만기 모델부터. `ETLDATE`/`baseYM` 워터마크가 이미 있습니다
- FREQ 계열 6개 매크로화, 12회 반복 월 오프셋을 jinja 루프로
- 3중 중첩 서브쿼리 → CTE, 최상류 `SELECT *` 제거
- NOLOCK → READ COMMITTED SNAPSHOT 검토
- 문서화 18.8% → 80% (마트·intermediate 우선)
- hook 로깅 폐기 → `run_results.json` 수집으로 대체

## 트레이드오프와 권고

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 전면 재편 (Phase 0~6) | dbt 도구 완전 활용, 온보딩 비용 급감, 원장 변경 사전 감지 | 8~10주. Phase 2·4에 회귀 리스크 집중 |
| B. Phase 0~2만 | 2~3주, 리스크 최소, 치명 결함 해소 | 하드코딩 98곳·고아 33% 방치 |
| C. 폴더 유지 + 접두사 규약 정식화 | 이동 비용 0 | 레이어 단위 실행 불가, 접두사-폴더 불일치를 먼저 풀어야 성립 |

권고는 **B를 즉시, A를 분기 단위로**. Phase 3이 무중단이라는 게 최대 지렛대라서 Phase 2까지 안정화되면 폴더 재배치는 리스크 없이 바로 얹을 수 있습니다.

반론도 남깁니다. 금융권 이관은 원본 프로시저와의 1:1 대조가 감사 요건인 경우가 많고 주석 처리된 원본 DDL과 구/신 테이블명 주석이 그 대조표입니다. 따라서 주석 정리와 Phase 5는 원본 프로시저 폐기 승인 이후로 미루는 게 옳습니다. 반면 Phase 0~2는 감사 추적성과 무관합니다 — 지금은 빌드가 안 되므로 대조할 결과물 자체가 없습니다.
