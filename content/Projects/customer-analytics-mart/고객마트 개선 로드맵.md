[[Projects/customer-analytics-mart/index|프로젝트 개요]]로 돌아가기

[[고객마트 dbt 구조 진단]]과 [[고객마트 리니지 분석]]에서 나온 것들을 "이어서 한다면 이 순서로"로 옮긴 글입니다. 운영 중인 마트를 멈추지 않고 표준 레이어까지 가는 게 목표이고, 그걸 가능하게 하는 dbt 성질이 둘 있습니다.

첫째, dbt에서 모델의 이름은 파일명이지 폴더 경로가 아닙니다. 파일을 다른 폴더로 옮겨도 `ref()`도 물리 테이블명도 안 깨집니다. 폴더 재배치가 완전 무중단인 이유입니다. 둘째, 이름을 바꿀 때 `{{ config(alias='기존물리명') }}`으로 물리 테이블명을 고정하면 BI 대시보드·외부 조회·Dagster asset이 영향을 받지 않습니다.

## 어디로 옮기나

| 지금 (프로시저 기준) | 모델 수 | 목표 (레이어 기준) |
|---|---|---|
| `sources/` 소스 yml | 0 | `staging/` 소스 yml — 원장 / DW / 캠페인 소스별로 분리 |
| `source_view/` | 1 | `staging/` |
| `subtable/` 부품 | 42 | 원장 1:1 추출 ~8 → `staging/`, 고객 단위 집계·룰 ~26 → `intermediate/`, 산출물 ~8 → `marts/` |
| `pom_procedure/` 조립 | 18 | 허브 + 프로시저 단계 체인 ~13 → `intermediate/`, 최종 마트 → `marts/` |
| `dentalMaturity_DashBoard/` | 1 | `marts/` (재작성 후) |
| `testfile/` 스크래치 | 2 | 삭제 |

대략 staging 9개, intermediate 39개, marts 13개 안팎이 됩니다. 배정 기준은 SQL 내용입니다. 이름은 `stg_원장__유효계약.sql` 식의 `stg_` / `int_` / `fct_` 규약을 따르되 물리명은 alias로 고정합니다.

## 순서

### 0. 빌드 복구 — 반나절

지금은 `dbt parse`가 안 되므로 나머지 논의가 전부 공중에 떠 있습니다. 하나씩 걷어냅니다.

1. `dbt_project.yml`의 models 블록 문법 수정 (시퀀스 하이픈을 없애고 중첩 매핑으로)
2. 미정의 var를 참조하는 스크래치 모델 삭제
3. 없는 매크로를 호출하는 테스트 파일 삭제
4. 동적 기준월 매크로에 `{% if execute %}` 가드와 빈 결과 기본값 추가

여기까지 하면 `dbt compile`이 에러 없이 끝납니다.

### 1. 안전망 — 1주

1. `packages.yml` 작성(dbt-utils, dbt-expectations)과 lock 파일 커밋
2. `profiles.yml`을 `~/.dbt/`로, 자격증명 로테이션, `.gitignore` 보강
3. 회귀 기준선 확보 — 마트별 행수와 핵심 컬럼 합계를 스냅샷으로 남깁니다. 이후 모든 단계는 이 기준선과 대조합니다
4. 그레인 키 4곳에 `unique` + `not_null` (허브 모델의 증권번호, 고객 통계 모델들의 고객키)
5. schema.yml의 모델명 오타 2건 수정 — 문서와 테스트가 여기서 유실되고 있었습니다
6. CI: `dbt deps && dbt parse && dbt compile`

테스트가 통과하고 기준선이 잡히면 다음 단계로 갑니다.

### 2. 조용히 틀리는 곳 수정 — 1~2주

1. 모델·소스 이중 정의 해소 — 소스 선언을 지우고 소비자를 `ref()`로. DAG가 이어지는 게 목표
2. 청약 주차별 타겟의 자리표시자 정수를 실제 날짜 파라미터로 — 원본 프로시저 대조와 업무 담당자 확인이 필수입니다
3. 치과 만기 모델을 `#temp` 없는 CTE 체인으로 다시 쓰고 `table` 명시
4. `add_month` 매크로의 무시되는 파라미터 정리 — 호출부 25곳의 결과가 바뀔 수 있어 기준선 대조 필수. 리스크가 크면 파라미터를 없애는 쪽이 안전합니다

통과 조건: 수정마다 기준선 행수·합계 일치.

### 3. 폴더 재배치 — 1주, 완전 무중단

`git mv`로 파일만 옮깁니다. 파일명도 모델명도 안 바뀝니다. materialization은 레이어별 기본 설정으로 위임하고, 모델 안의 중복 `{{ config(materialized='table') }}` 40여 개를 지웁니다.

```yaml
models:
  my_dbt_project:
    staging:      {+materialized: view,      +tags: [staging]}
    intermediate: {+materialized: ephemeral, +tags: [intermediate]}
    marts:        {+materialized: table,     +tags: [marts]}
```

schema.yml도 레이어별로 나눕니다. 통과 조건: `dbt run` 결과가 2단계 종료 시점과 동일. 물리 테이블명이 하나도 안 변했으니 다운스트림 영향은 0입니다.

### 4. 소스 계약 — 2~3주

하드코딩 98곳을 `source()`로 파일 단위로 쪼개 전환하고 건건이 기준선과 대조합니다. 순서는 참조 빈도순 — 기간계(실시간 원장)의 계약 뷰 → DW 상품 마스터 → 캠페인 통제 테이블. `sources.yml`의 database/schema를 `env_var()`로 빼서 dev/prod 분리 기반을 만듭니다. 목표는 리니지 고아 21개 → 0개.

### 5. 이름 정리 — 2주, alias로 무중단

`stg_` / `int_` / `fct_` 파일명으로 바꾸고 `config(alias=)`로 물리명을 고정합니다. 접두사 오타, 트레일링 언더스코어, 대소문자 혼용을 이때 함께 정리합니다. alias 제거는 다운스트림 마이그레이션이 끝난 뒤 별도 일정입니다.

### 6. 성능·품질 — 지속

- incremental 도입: 2022년부터 전체 재계산하는 만기 모델부터. `ETLDATE` / `baseYM` 워터마크가 이미 있습니다
- 접촉 빈도 계열 6개 매크로화, 12번 반복되는 월 오프셋을 jinja 루프로
- 3중 중첩 서브쿼리 → CTE, 최상류 `SELECT *` 제거
- `NOLOCK` → `READ COMMITTED SNAPSHOT` 검토
- 문서화 18.8% → 80% (marts·intermediate 우선)
- hook 로깅은 폐기하고 `run_results.json` 수집으로 대체

## 어디까지 할 것인가

0~2단계만 하면 2~3주에 치명 결함이 사라지고 리스크도 가장 적습니다. 대신 하드코딩 98곳과 고아 모델 33%는 그대로 남습니다. 0~6단계 전부는 8~10주이고 회귀 리스크가 2·4단계에 몰립니다. 폴더는 두고 접두사 규약만 정식화하는 길도 있지만, 접두사와 폴더가 안 맞는 문제를 먼저 풀어야 성립하고 레이어 단위 실행은 여전히 안 됩니다.

권하는 순서는 0~2단계를 바로, 나머지는 분기 단위로입니다. 3단계가 무중단이라는 게 가장 큰 지렛대라서, 2단계까지 안정되면 폴더 재배치는 리스크 없이 바로 얹을 수 있습니다.

한 가지는 미뤄야 합니다. 금융권 이관은 원본 프로시저와의 1:1 대조가 감사 요건인 경우가 많고, 주석 처리된 원본 DDL과 구/신 테이블명 주석이 그 대조표입니다. 주석 정리와 5단계 이름 변경은 원본 프로시저 폐기 승인 이후로 미루는 게 맞습니다. 0~2단계는 감사 추적성과 무관합니다. 지금은 빌드가 안 되니 대조할 결과물 자체가 없습니다.
